### 1.1. Как обеспечена уникальность работы

Задание требует использовать **фамилию и группу** студента в `msg.topic`, именах,
payload и названиях потоков. Применена такая схема:

| Где | Как выглядит |
|-----|--------------|
| `msg.topic` | `lab2/krupa-ii241/basic`, `lab2/krupa-ii241/function`, … |
| Топик MQTT | `student/krupa-ii241/lab2/sensor` |
| Названия потоков (вкладок редактора) | `01 · inject → debug (ИИ-241)` — во всех 13 |
| Подписи на полотне (ноды `comment`) | `2.1 inject → debug · ИИ-241` — во всех 13 |
| `msg.payload` и ответы API | `"student": "Крупа Ксения (ИИ-241)"` — 40 мест |
| Имена inject-нод | `Каждые 5 сек: Крупа Ксения (ИИ-241)` |
| Файл лога из 2.11 | `/data/krupa-ii241-log.jsonl` |
| Имя Telegram-бота | `tvl_lab2_krupa_bot` — здесь шаблон задания задаёт только фамилию |

Почему в топиках, URL и именах файлов стоит латинский слаг `krupa-ii241`,
а не `Крупа-ИИ-241`: кириллица в MQTT-топике формально допустима, но ломается
при работе с частью брокеров и утилит, которые ожидают ASCII. Поэтому топик и путь
к файлу сделаны латиницей, а во всех читаемых местах (имена нод, подписи, payload,
ответы API) используется полный вариант **«Крупа Ксения (ИИ-241)»**.

Отдельно про эндпоинт `GET /api/info`: по заданию он обязан возвращать JSON
**ровно с двумя полями**. Чтобы требование не нарушить и при этом показать и фамилию,
и группу, оба значения объединены в одном поле:

```json
{
  "student": "Крупа Ксения (ИИ-241)",
  "lab": 2
}
```

Так формат ответа остаётся единообразным: во всех остальных эндпоинтах поле
`student` содержит то же значение.

Группа также передаётся контейнеру переменной окружения `LAB2_GROUP` (поток 2.12
показывает её в Debug) — файл `lab2/scripts/lab2.env`, подключается через
`docker run --env-file`. Переменные передаются файлом в UTF-8, а не флагами `-e`:
в командной строке Windows русский текст проходит через ANSI-кодировку и доходит
до контейнера искажённым.

## 2. Способ установки и версии

### 2.1. Почему Docker

Задание рекомендует Docker, и у него здесь два реальных преимущества:

1. **Изоляция.** Node-RED не ставится глобально в систему и не тянет за собой сотни пакетов в `%APPDATA%\npm`.
2. **Volume.** Каталог `/data` внутри контейнера смонтирован на папку репозитория, поэтому `flows.json`, лог-файл из потока 2.11 и настройки лежат на хосте и **переживают пересоздание контейнера**. Это понадобилось в п. 2.11, где требовалось показать сохранение данных между перезапусками.

### 2.2. Команда запуска

```powershell
docker run -d --name krupa-lab2-nodered `
  -p 1880:1880 `
  -v "C:\Users\Ksenia\study\visual-programming-labs-Krupa\lab2\node-red-data:/data" `
  -e LAB2_STUDENT=Krupa `
  -e LAB2_LAB=2 `
  --restart unless-stopped `
  nodered/node-red:latest
```

Разбор параметров:

| Параметр | Смысл |
|----------|-------|
| `-d` | контейнер работает в фоне |
| `--name krupa-lab2-nodered` | понятное имя, видно в `docker ps` |
| `-p 1880:1880` | порт 1880 хоста → порт 1880 контейнера (редактор на <http://localhost:1880>) |
| `-v <хост-папка>:/data` | обязательный по заданию volume: папка хоста ↔ `/data` в контейнере |
| `-e LAB2_STUDENT`, `-e LAB2_LAB` | переменные окружения для потока 2.12 |
| `--restart unless-stopped` | контейнер поднимается сам после перезагрузки ОС |
| `nodered/node-red:latest` | официальный образ с уже установленным Node-RED |

### 4.2. Function node (`flow-02-function.json`)

Три inject-ноды по очереди отправляют в одну функцию число `5`, строку `Крупа Ксения` и объект с массивом оценок — чтобы три ветки `if/else` отработали все.

Код функции использует `const`, `let`, `if/else if/else`, циклы `for`, массив и объект:

```js
const input = msg.payload;
let inputType = typeof input;
let values = [];

if (Array.isArray(input)) { inputType = "array"; values = input.slice(); }
else if (input !== null && typeof input === "object") { inputType = "object"; values = Array.isArray(input.scores) ? input.scores.slice() : []; }
else if (typeof input === "number") { inputType = "number"; for (let i = 1; i <= input; i++) { values.push(i); } }
else { inputType = "string"; values = String(input).split(/\s+/).filter(Boolean).map(w => w.length); }

let sum = 0;
for (let i = 0; i < values.length; i++) { sum += values[i]; }
const avg = values.length > 0 ? sum / values.length : 0;
```

Функция возвращает **объект с полем `payload`**:

```js
msg.payload = {
    student: msg.student,
    inputType: inputType,
    values: values,
    count: count,
    sum: sum,
    avg: Number(avg.toFixed(2)),
    verdict: verdict
};
return msg;
```

### 4.7. MQTT с публичным брокером (`flow-07-mqtt.json`)

* Брокер: `broker.hivemq.com:1883` (публичный, без авторизации). Альтернатива из задания — `test.mosquitto.org:1883`.
* Топик: `student/krupa-ii241/lab2/sensor`.
* **Ветка публикации:** inject раз в 5 секунд → function, которая формирует случайное «показание датчика» 18…30 °C → `mqtt out`.
* **Ветка подписки:** `mqtt in` на тот же топик → `debug`.

Так как обе ветки в одном потоке, опубликованное сообщение возвращается из брокера и попадает в Debug — это и есть доказательство, что публикация и подписка работают.

Полезное свойство MQTT, которое здесь видно: брокер не хранит историю, он только раздаёт сообщения текущим подписчикам. Если подписка не активна в момент публикации, сообщение теряется (при `QoS 0` и `retain = false`).

### 4.11. Чтение и запись файла (`flow-11-files.json`)

Один поток, две ветки.

**Запись:** `inject → function → file out`.
Файл: `/data/krupa-ii241-log.jsonl`, формат **JSON Lines** — одна строка = один JSON-объект.
Function-нода формирует запись и подставляет путь в `msg.filename` (в самой ноде путь стоит по умолчанию, но переопределяется из сообщения).

```json
{"ts":"2026-01-15T12:34:56.789Z","student":"Крупа Ксения (ИИ-241)","lab":2,"sensor":"temperature","value":23.7,"unit":"C"}
```

**Чтение:** `inject → file in → function → debug`.
Файл читается целиком как строка UTF-8, function-нода разбирает его построчно, пропускает повреждённые строки (`try/catch` внутри цикла) и считает статистику: количество записей, первое и последнее значение, минимум, максимум, среднее.

**Сохранение между перезапусками.** Файл лежит в `/data`, а `/data` — это смонтированная папка репозитория `lab2/node-red-data`, то есть данные физически на хосте. После `docker restart krupa-lab2-nodered` ветка чтения по-прежнему возвращает все ранее записанные строки.

### 4.12. Работа с контекстом (`flow-12-context.json`)

Продемонстрированы сразу три механизма хранения состояния.

**1. Flow context — счётчик, живущий между сообщениями:**

```js
let counter = flow.get("krupa_counter");
if (typeof counter !== "number") { counter = 0; }
counter = counter + 1;
flow.set("krupa_counter", counter);
```

Inject раз в 3 секунды увеличивает счётчик на 1. Отдельный inject «сбросить счётчик» возвращает его в 0 — так видно, что значение действительно живёт в контексте, а не пересоздаётся при каждом сообщении.

**2. Global context — журнал последних пяти значений:**

```js
let history = global.get("krupa_history");
if (!Array.isArray(history)) { history = []; }
history.push({ n: counter, at: new Date().toISOString(), value: msg.payload });
if (history.length > 5) { history = history.slice(history.length - 5); }
global.set("krupa_history", history);
```

Отличие от flow context: область видимости — весь рантайм Node-RED, значение доступно из любого потока, а не только из текущего.

**3. Environment variables — настройки, приходящие снаружи:**

```js
const envStudent = env.get("LAB2_STUDENT") || "(переменная не задана)";
const envLab = env.get("LAB2_LAB") || "(переменная не задана)";
```

Переменные переданы контейнеру флагами `-e LAB2_STUDENT=Krupa -e LAB2_LAB=2` при `docker run`. Это позволяет менять поведение потока, не редактируя его: например, указать другую фамилию или другой номер лабораторной.

Важное наблюдение: **flow и global context живут в памяти процесса Node-RED**. Редеплой потока они переживают, а перезапуск контейнера — нет. Для настоящей персистентности нужен либо файл (см. 2.11), либо `contextStorage` с файловым хранилищем в `settings.js`, либо база данных (ачивка №10 — SQLite).

![Поток REST CRUD](../screenshots/13-rest-crud.png)

### 5.2. Хранение: почему flow context

Задание разрешает выбрать между `flow context`, `global context` и файлом. Выбран **flow context** (переменная `krupa_tasks`), и вот обоснование:

1. **Нет внешних зависимостей.** Не нужен ни модуль для SQLite, ни `fs` в function-ноде (в function-нодах по умолчанию `fs` недоступен — его надо отдельно подключать в `Setup → libs`), ни лишние ноды.
2. **Данных ровно столько, сколько нужно для демонстрации.** CRUD — это про контракт API, а не про объём хранения.
3. **Состояние живёт между сообщениями и переживает редеплой** — этого достаточно, чтобы последовательность «POST → GET → PATCH → DELETE» работала как единый сценарий.
4. **Известное ограничение честно названо:** перезапуск контейнера обнуляет контекст. Чтобы поток всегда был в рабочем состоянии, есть inject «сидировать задачи» с `once: true`, который после каждого деплоя наполняет контекст тремя тестовыми записями (и ничего не делает, если данные уже есть).
5. **Путь к продакшену очевиден и не требует менять API:** достаточно заменить четыре обращения к `flow.get/flow.set` на работу с файлом (поток 2.11) или с SQLite (ачивка №10) — все URL, коды и формат ответов останутся теми же.

### 5.3. Как устроена валидация

В каждой POST/PATCH-ноде работает общий набор проверок:

| Проверка | Код ответа |
|----------|-----------|
| тело запроса не объект (или массив) | 400 |
| `title` отсутствует или не строка | 400 |
| длина `title` вне диапазона 3…100 | 400 |
| `done` передан, но не boolean | 400 |
| PATCH без единого изменяемого поля | 400 |
| `id` не целое число | 400 |
| записи с таким `id` нет | 404 |

Все ответы об ошибках имеют единый формат, поэтому клиенту не нужно угадывать структуру:

```json
{
  "error": "Bad Request",
  "message": "Длина title должна быть от 3 до 100 символов",
  "student": "Крупа Ксения (ИИ-241)",
  "extra": { "received": "ok" }
}
```

## 8. Выводы

1. **Node-RED действительно позволяет собрать рабочий бэкенд без написания «каркаса».** HTTP-сервер, парсинг тела запроса, JSON-сериализация ответа, MQTT-клиент, работа с файлами — всё это уже реализовано нодами. Код пишется только там, где нужна бизнес-логика, то есть в function-нодах.

2. **Главная экономия — на инфраструктуре, а не на логике.** Поток `http in → function → http response` заменяет сразу Express-роут, middleware для `express.json()` и сериализацию ответа. Но валидацию, коды состояния и формат ошибок всё равно приходится продумывать самому — low-code не отменяет проектирования.

3. **«Low-code» ≠ «без кода».** Самые содержательные части работы — CRUD-логика, ветвление, работа с контекстом, разбор файла — это обычный JavaScript внутри function-нод. Визуальным оказалось то, что вокруг: маршрутизация сообщений, конфигурация подключений, обработка ошибок.

4. **Состояние — самое неочевидное место.** Пришлось разбираться, чем отличаются `msg`, flow context, global context и переменные окружения, и где что живёт: `msg` — на одно сообщение, flow context — на один поток до редеплоя/рестарта, global — на весь рантайм, env — задаётся снаружи при запуске. Ошибка в выборе уровня хранения ломает логику незаметно: поток работает, пока не перезапустишь контейнер.

5. **Порог входа низкий, а потолок высокий.** Базовый поток `inject → debug` собирается за минуту, но дальше приходится разбираться с MQTT-брокерами, JWT, SQLite, WebSocket, написанием собственных нод — то есть инструмент растёт вместе с задачей, а не упирается в потолок, как большинство конструкторов.

6. **Отладка визуального потока удобнее текстовой.** Панель Debug показывает сообщение целиком на каждом участке цепочки, и не нужно расставлять `console.log` и перезапускать сервер, чтобы понять, где сообщение потерялось. На потоке MQTT это особенно заметно: видно и то, что было отправлено, и то, что вернулось от брокера.

7. **Docker + volume — обязательная связка для учебной работы.** Без volume данные из потока 2.11 исчезали бы вместе с контейнером, и требование «показать сохранение между перезапусками» выполнить было бы невозможно. Заодно volume решает проблему переноса: `flows.json` лежит в папке репозитория, а не в недрах виртуальной машины Docker.

8. **Самое трудоёмкое в этой лабораторной — не собрать поток, а сделать его воспроизводимым и объяснимым.** Поток, который работает «здесь и сейчас», и поток, который можно импортировать из файла, задокументировать и защитить, — это две разные работы. Больше всего времени ушло на вторую: комментарии на полотне, отдельные `flow-NN-*.json`, описание эндпоинтов и обоснование выбранного хранилища.
